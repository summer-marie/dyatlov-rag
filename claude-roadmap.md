# Dyatlov RAG — Backend Build Roadmap

Context doc for resuming work across sessions. Follows `AGENTS.md` rules: one small step at a time, explicit permission before moving on, no git operations by Claude.

**Frontend contract (already built, in `public/index.html`):**
- `POST http://localhost:3000/ask` with JSON body `{ question }`
- Expects JSON response `{ answer, sources }` where `sources` is an array of filenames

## Steps

- [x] **Step 1 — Ingestion**: `retriever.js` — `loadKnowledgeBase()` async function reads all `.md` files from `knowledge-base/`, returns array of `{ source, text }` chunk objects.
- [x] **Step 2 — Retrieval**: `retriever.js` — `searchChunks(question, chunks, topN)` extracts keywords from the question, scores each chunk by keyword frequency, filters out zero-score chunks, sorts by relevance, returns top matches (each still tagged with `source`).
- [x] **Step 3 — Empty Retrieval Handling**: no standalone code needed — `searchChunks()` already returns `[]` on 0 matches. The actual bypass-the-LLM check is merged into Step 6's route handler.
- [x] **Step 4 — Prompt Augmentation**: `promptBuilder.js` — `buildPrompt(question, chunks)` merges retrieved chunks into a context block and returns a `messages` array (system + user) with strict "answer ONLY from context" instructions, ready for the Groq chat completions API.
- [x] **Step 5 — Generation**: `generator.js` — `generateAnswer(messages)` sends the messages array to Groq's chat completions endpoint via native `fetch` (model: `llama-3.1-8b-instant`), throws on API errors, returns the answer text. Fully separate from retrieval/prompt logic.
- [x] **Step 6 — Routing**: `server.js` — Express app loads the knowledge base once at startup, serves `public/` statically, and exposes `POST /ask`: retrieves chunks → bypasses the LLM with a hardcoded "I don't know" on 0 results (Step 3) → builds prompt → calls Groq → returns `{ answer, sources }` (sources taken from retrieved chunks, not the LLM).
- [x] **Step 7 — Env/Config**: `.env` holds `GROQ_API_KEY` and `GROQ_MODEL`, loaded via `dotenv` in `generator.js`.
- [x] **Step 8 — Manual End-to-End Test**: server started via `node server.js`, tested `POST /ask` directly with curl — relevant question returned a grounded answer with correct `sources` array; unrelated question returned the hardcoded "I don't know" with `sources: []`. Browser test against `public/index.html` still recommended.
- [x] **Step 9 — Edge Cases**: empty question input verified (returns `400 { error: "Question is required." }`); no-matching-chunks verified (bypasses LLM, hardcoded message). Groq API error/timeout path is implemented (`try/catch` → `500`) but not live-tested (would require simulating an API failure).

- [x] **Step 10 — Manual NL Question QA**: created `tests/manual-questions.md` with 4 hand-run questions against the live `/ask` endpoint (direct fact, comparative/superlative, spatial/numeric, out-of-scope refusal). Direct-fact and refusal cases passed. Comparative case was a partial pass (hedged but correct). Spatial case **failed** — the LLM stated "70 meters from the tent," a number not present anywhere in the knowledge base, because keyword retrieval didn't pull the chunk (`06_first_five_bodies.md`) that actually has the real distances (300/480/630 m from the cedar tree, not the tent). Also flagged: `sources` can list chunks that didn't meaningfully contribute to the answer, since "night"/"moon"/"weather" aren't stop words and can drag in loosely-matching chunks. No code changed — findings logged for a future retrieval-tuning decision, not acted on yet.

- [x] **Step 11 — Retrieval Refactor: Chunk by Heading**: `retriever.js`'s `loadKnowledgeBase()` now splits each `.md` file into smaller chunks by `##` markdown heading (via new `splitIntoSections()` helper) instead of treating a whole file as one chunk. `server.js`'s `sources` mapping now dedupes filenames (`[...new Set(...)]`) since multiple chunks can share a source file. Driven by the Step 10 finding that the tent-distance question pulled weakly-related whole-file chunks and the LLM hallucinated a number. Re-test after the change: hallucination is gone and two other test answers got more precise, but the tent-distance question still doesn't retrieve the right section — confirmed via direct scoring that `06_first_five_bodies.md`'s "## Location" section uses "camp"/"corpses"/"bodies" instead of "tent"/"hikers"/"found", so it scores too low regardless of chunk size. This is a vocabulary-mismatch limitation of keyword matching, not something chunking can fix — logged in `tests/manual-questions.md` as a known limitation of the current no-embeddings retrieval approach, not acted on further without a decision to revisit that architecture choice.

- [x] **Step 12 — Synonym Matching + Length-Normalized Scoring**: `retriever.js` now has a `SYNONYMS` map (built from grepping real term frequency in `knowledge-base/*.md`) and `expandKeywords()` so question wording (hikers/tent/found/died/injuries/distance) also matches knowledge-base wording (group/camp/discovered/perished/trauma/metres). Also changed `searchChunks` scoring from raw keyword-occurrence counts to length-normalized density (`occurrences / wordCount`), since long chunks were winning purely by being longer, not more relevant — this is what was actually blocking the Step 11 tent-distance fix. That normalization had a side effect (tiny leading "# Title" fragments getting inflated scores), fixed by adding `MIN_SECTION_WORDS = 10` to `splitIntoSections()` so short leading fragments merge into the next real section instead of standing alone. Default `topN` in `searchChunks` raised from 3 → 6 (confirmed via direct scoring script that the correct chunk for the tent-distance question ranked 6th). Re-tested all 8 questions in `tests/manual-questions.md` (original 4 + 4 new synonym-targeted cases) — all pass, including the previously-failing tent-distance question, with no regressions.

- [x] **Step 13 — More Synonym Coverage**: read `02_the_group.md`, `07_remaining_four_bodies.md`, `04_search_and_discovery.md` directly to self-generate 4 more test questions (no extra context needed from the user). Found two more vocabulary gaps and added them to `retriever.js`'s `SYNONYMS` map: `trip`/`journey`/`expedition`/`route`, and `buried`/`covered`. All 4 new questions pass, and a regression check on the Step 12 tent-distance and moon-weather questions confirmed no breakage. Total manual test coverage now 12 questions, all passing, logged in `tests/manual-questions.md`.

- [x] **Step 14 — More Synonym Coverage, Round 2**: read `01_overview.md`, `09_investigation.md`, `18_recent_developments.md`, `19_legacy.md`, `16_theory_animal_attack.md`, `17_other_theories.md` directly to self-generate 4 more test questions. All 4 new questions pass; regression-checked the tent-distance question again with no breakage. Total manual test coverage now 16/16 passing, logged in `tests/manual-questions.md`.

- [x] **Step 15 — Stop-Word Tuning**: addressed the flagged "moon"/"night" sources issue from Step 10. Added `that` to `STOP_WORDS` in `retriever.js` (filler in all 19 knowledge-base files). Tried adding `night` too, but reverted after it broke question 16 ("blizzard...night of the tragedy"), which depends on matching the literal phrase "the weather on the night of the tragedy was harsh" in `09_investigation.md` — `night` is filler in most files but load-bearing in that one. Full regression run (questions 1, 2, 3, 4, 9, 16) confirmed the final state (only `that` added) has no breakage. Logged in `tests/manual-questions.md` Step 15.

- [x] **Step 16 — Browser Test + IDF Weighting Fix**: user manually tested `public/index.html` in a real browser (Chrome MCP extension wasn't connected) and found a real bug: "How many of the hikers were women?" returned "I do not know," even though `02_the_group.md` literally states "eight men and two women." Root cause: the correct chunk never uses "hikers" (it says "group"/"people"), and "group" is so common in the corpus (17/19 files) that it drowned out the one truly rare, distinguishing keyword ("women", in 1 file) in the density-based scoring. Fixed by adding **IDF (inverse document frequency) weighting** to `searchChunks` in `retriever.js` — each keyword's occurrence count is now weighted by `totalChunks / documentFrequency(keyword)`, so common keywords contribute little and rare ones dominate, before the existing length normalization. Full regression across all 16 prior questions passed, plus the new one — 17/17. This was the first bug caught via actual manual browser use rather than a designed test case. Logged in `tests/manual-questions.md` Step 16.

- [x] **Step 17 — Groq API Error Path (Live-Tested)**: closed the last open item from Step 9. Please try again."}` with no leaked details, the server logs the real error via `console.error`, the process doesn't crash, and a restart with the correct key recovers cleanly. No code changes — this was pure verification. Logged in `tests/manual-questions.md` Step 17.

- [x] **Step 18 — Semantic Retrieval Migration (OpenAI embeddings)**: replaced keyword/TF-IDF/synonym retrieval with embedding-based cosine similarity, per the plan in `notes.md`. New `embedder.js` (one-time build script) reuses `loadKnowledgeBase()`/`splitIntoSections()` to embed each heading-section chunk with `text-embedding-3-small`, writing `embeddings.json` (77 records). `retriever.js` rewritten: kept `loadKnowledgeBase`/`splitIntoSections` (still used by `embedder.js`), added `loadEmbeddings()`, `cosineSimilarity()`, `embedQuery()`, and a new async `searchChunks()` that embeds the question and ranks by similarity. Added `MIN_SIMILARITY = 0.25` threshold (calibrated against real data: relevant questions scored 0.50-0.54 top, an irrelevant one topped at 0.146) to preserve the Empty Retrieval Handling rule, since cosine similarity never naturally returns "0 results" otherwise. `server.js` updated minimally: startup now calls `loadEmbeddings()` instead of `loadKnowledgeBase()`, and `searchChunks()` is now `await`ed (required since query embedding is a network call). Default `topN` raised from the initial 5 to 6 after live calibration showed the correct chunk for "How many of the hikers were women?" ranked 6th (0.429), just outside top 5 — same shape of off-by-one-rank issue as the old retriever's Step 12 finding. `embeddings.json` added to `.gitignore` (regenerable via `node embedder.js`). Re-verified the women/hikers synonym case (now correct), the tent-distance spatial case (now correct, real 300-630m figures, no fabrication), and the irrelevant-question bypass (still correctly returns 0 results). All of `SYNONYMS`/`STOP_WORDS`/IDF/keyword scoring logic from Steps 12-16 was removed — semantic search now handles vocabulary gaps without a hand-maintained synonym list.

- [x] **Step 19 — Hybrid Retrieval (keyword-boosted embeddings)**: fixed a real regression found via manual browser testing — "how many hikers in the group were women" (slightly different phrasing than the Step 18 test case) returned "I do not know" because the answer-containing chunks ranked 10th and 31st out of 77, outside `topN=6`. Per user's design: kept embeddings as the primary signal, added `getQueryKeywords()` + `keywordBoost()` in `retriever.js` — a chunk's score is now `cosineSimilarity + boost`, where the boost rewards exact matches on query terms inversely weighted by how many chunks contain them (rare terms like names/numbers/"women" contribute meaningfully, common terms contribute almost nothing). Boost is applied before the similarity cutoff so strong lexical matches can survive even with weak raw similarity. `MIN_SIMILARITY` lowered 0.25 → 0.2, `topN` raised 6 → 8 (only after hybrid scoring was in place, per user's explicit guidance not to jump straight to 12). Verified: the failing question now retrieves the correct chunk at rank 1 (score 0.611, was 0.302-0.373 on raw similarity), consistently across repeated runs. Re-ran tent-distance, avalanche, and empty-bypass regression checks — all still pass. **Separate finding (not a retrieval issue):** repeated identical queries showed real generation-layer inconsistency from `llama-3.1-8b-instant` — same retrieved context, but answer quality varied between a clean correct answer and a confused/self-contradictory one across runs, and a separate query incorrectly named "Yudin" (who left the expedition and survived) as injured instead of Thibeaux-Brignolles. Flagged for a future decision (e.g. lowering temperature), not acted on.

- [x] **Step 20 — Post-Hybrid Retrieval Validation (3-question set)**: deliberately held off on any `generator.js` changes to isolate whether the earlier answer-inconsistency (Step 19) was a retrieval problem or a generation problem. Tested one structured-fact, one names/list, and one conceptual question; for each, inspected retrieved chunks directly before checking the live answer. All three retrieved the correct source chunk (structured fact: `07_remaining_four_bodies.md` "## Location" at rank 2; names/list: `02_the_group.md`'s table at rank 1; conceptual: `13_theory_paradoxical_undressing.md` at ranks 1-2 with scores 0.873/0.841), and all three answers were accurate. Repeated the structured-fact question 3 times: 2 identical correct answers, 1 `500` from the pre-existing Groq rate-limit path (not output randomness). **Conclusion: retrieval is clearly correct and answers were consistent in this round — the Step 19 inconsistency did not reproduce, so a generation-consistency change (e.g. lowering temperature) is not justified yet.** No changes made to `generator.js`.

## Known Limitations / TODO
- **Substring-based keyword boost can false-positive on unrelated word senses.** Found during Step 20: the query "How deep was the snow..." boosted a chunk containing "deep brown tan" (skin color, unrelated) to rank 1, because `keywordBoost()` in `retriever.js` does a plain `.includes()` substring match and "deep" happens to appear in only 1 of 77 chunks (max rarity weight), with no awareness that it's a different word sense than "deep" meaning snow depth. Didn't break the answer this time (the correct chunk was still within `topN=8`), but it's a real gap. **Future improvement, not yet implemented:** match whole words/tokens instead of substrings (e.g. split chunk text into a word set and check membership, rather than `lowerText.includes(keyword)`), which would at least prevent partial-string false matches; reducing accidental rarity boosts from incidental adjective matches like "deep" would need either part-of-speech awareness or simply accepting it as an inherent limit of lexical boosting and leaning more on embeddings as the primary signal.
- **Generation-consistency tuning (temperature, etc.) intentionally deferred** — only revisit `generator.js` if a future test shows either: (a) the same retrieved chunks producing meaningfully different answers across repeated runs, or (b) the model adding unsupported speculation despite correct, complete context being present.

## Notes
- Tech stack: Node.js + Express, CommonJS modules (`"type": "commonjs"` in `package.json`), vanilla JS, no TypeScript.
- Retrieval is hybrid: OpenAI `text-embedding-3-small` cosine similarity as the primary signal, with a rarity-weighted exact-match keyword boost layered on top (`retriever.js`). Precomputed via `embedder.js` into `embeddings.json` (regenerate with `node embedder.js` after knowledge-base changes).
- Every chunk must carry its `source` filename through the whole pipeline (retrieval separation + source tracking rules in `AGENTS.md`).
